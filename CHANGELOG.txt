========================================================================
  BOB2 Windows 10/11 Fix - Changelog
========================================================================

Version numbers here refer to THIS FIX PACKAGE, not to the game.
The game reports its own version (2.12 / 2.13) on its main menu.

Where to check which fix version you have:
  - In the game folder:  BOB2-Win11-Fix.version
  - In bob2guard.log:    first line, written every time the game runs
  - In the setup tool:   shown in the menu header and in
                         "Check Installation Status"
All three should agree. If bob2guard.log reports an older version than
the setup tool, a stale dinput8.dll is deployed - re-run the crash fix
step to update it.


v1.6.26  (2026-08-23)
---------------------
  Uninstall was undoing the wrong thing. Found while checking whether a
  tester should uninstall before updating. He should not have, and now it
  would not have mattered.

  - FIXED: uninstalling DOWNGRADED THE GAME. It restored Bob.exe.v212 or
    Bob.exe.v206 - backups of earlier GAME versions, taken before applying
    a patch - so "remove this mod" quietly meant "put the game back to
    2.12". That undoes something the user asked for rather than something
    this mod imposed.

    It now restores Bob.exe.unscaled, the pristine copy taken before the
    menu rescale and the DebugBreak import fix, which is exactly and only
    what this mod changed. The version backups are left alone and named in
    the log, so anyone who genuinely wants an older executable can put one
    back by hand.

    Since 1.6.24 this was worse than it sounds: the GUI answers prompts
    automatically, so the downgrade no longer even asked.

  - FIXED: Bob.exe.unscaled could itself be stale. Neither patch step
    removed it after replacing Bob.exe, so a copy taken at 2.06 survived a
    2.13 patch and sat there as a downgrade waiting to happen - the menu
    rescale patches "the pristine original", and uninstall restores it.
    Step-ApplyV212 and Step-ApplyV213 now clear it, so the next rescale
    takes a fresh copy from the newly patched executable.

  UPDATING does not require uninstalling, and never did. Replace the
  BOB2-Win11-Fix folder and run Install and repair.

v1.6.24  (2026-08-11)
---------------------
  "I click Fix and nothing happens, then it freezes." Reported against
  1.6.23 by the same tester, whose game is the A2A digital download and
  therefore starts at v2.06 rather than 2.13.

  - FIXED: every Fix button could hang the Install and repair window.

    The Step-* functions were written for a console tool and still ask
    questions: Read-Host for an answer, RawUI.ReadKey for a keypress. The
    GUI dot-sources that same file with -AsLibrary and runs it with NO
    CONSOLE ATTACHED, so those calls waited forever for input that could
    never arrive, with nothing on screen to say why. The window simply
    stopped responding.

    Every prompt reachable from the GUI now checks a $script:NonInteractive
    flag set by -AsLibrary:
      - Cosmetic pauses are skipped.
      - "Do you want to do X?" answers itself yes - pressing Fix WAS the
        answer, and re-asking invisibly would abort the requested action.
      - Genuine blockers throw NEEDS-FILE / NEEDS-ANSWER, which the GUI
        now shows in a dialog instead of burying in the collapsed log.
      - Steps that would launch the game or open Windows settings are
        skipped rather than surprising a GUI user.

    So a missing patch now reads "Place BDG v2.13 patch in the
    BOB2-Win11-Fix folder, then continue" instead of freezing.

  - FIXED: the bundled dgVoodoo2 was never found. The folder we ship is
    called dgv2873 and that name was missing from the list of folders the
    installer searches, so it fell through to hunting for a zip, found
    none, and asked the user to supply dgVoodoo2 - which was already
    sitting in the folder beside it.

  - FIXED: and once found, it still would not install. The copy step looked
    only in MS\x86, MS/x86 and x86, the layout of an official dgVoodoo2
    zip. Our bundled copy keeps the DLLs at the top level, so the step
    reported "could not find MS\x86". It now also accepts the folder
    itself, and tests for an actual D3D9.dll rather than just a directory
    name, so an empty x86 folder cannot win and silently install nothing.

  Verified on a clean folder rather than by reading the code: all three
  steps complete in under 300ms and deliver the four DLLs, dinput8.dll,
  dgVoodoo.conf and the version stamp. With the 2.13 patch absent, the
  step returns its NEEDS-FILE message in 114ms instead of hanging.

v1.6.22  (2026-08-11)
---------------------
  All three from the first outside tester - a Windows 11 user new to the
  sim, which is exactly the case the wizard is written for.

  - FIXED: the desktop shortcut was indistinguishable from the game's own.
    It was named "Battle of Britain II" and borrowed Bob.exe's icon, so it
    sat next to the shortcut the game installer creates looking identical.
    The tester reported that clicking it "loads the sim directly - the
    launcher does not appear": he was clicking the game's one, with no way
    to tell them apart. Consequence was bigger than a cosmetic slip, since
    every fix the launcher applies on the way to PLAY - the HIGHDPIAWARE
    removal in particular - was silently skipped, which in turn explains
    his unreadable in-game menus.

    Now "Battle of Britain II - Modern Fix" with its own RAF roundel icon
    (assets\BOB2ModernFix.ico). Setup removes the old ambiguous shortcut,
    but only after confirming it points at our own BOB2.bat - a shortcut
    aimed at the game is never touched.

  - DOCUMENTED: why the in-game videos do not play. They are Indeo Video 5
    (IV50). Microsoft withdrew the Indeo codecs from Windows over a remote
    code execution vulnerability, so a stock Windows 10 or 11 has nothing
    to decode them with and the game can hang trying. Setup disables them
    (SKIP_VIDEOS, SKIP_QUICKVIDEOS, INTRO_VIDEO). That was happening
    silently and read as a fault. Behaviour unchanged - it is now
    explained in README.txt.

    CORRECTED same day: the first version of that note claimed the videos
    could not be restored at all. Wrong. Microsoft's codec is gone, but
    FFmpeg has an independently written Indeo decoder and codec packs such
    as K-Lite install it. Bob.exe imports ole32 and neither avifil32 nor
    msvfw32, indicating DirectShow rather than Video for Windows - which
    is what those packs hook into. Installing K-Lite and re-enabling the
    three settings has a good chance of working. Caught by a forum reader
    who remembered doing exactly that.

  - DOCUMENTED: antivirus quarantining unsigned PowerShell, and the
    Mark-of-the-Web "Unblock" step. Both produce the identical symptom -
    a console window flashes and no launcher appears - and between them
    they are the likeliest reason a first run fails on someone else's
    machine.

v1.6.17  (2026-08-06)
---------------------
  - FIXED: Done in Install and repair, and Finish in the wizard, did not
    take you back to the main screen.

    Both looked for the launcher with
      Get-Process powershell | where MainWindowTitle -eq 'Battle of Britain II'
    which never matches. The launcher runs inside powershell.exe with its
    console hidden, and Windows can report that hidden console as the
    process's main window - so the WPF window is never seen.

    They now enumerate top-level windows and match on the title, which was
    verified both ways: with the launcher closed the finder correctly
    reports nothing and the fallback starts it; with it open the finder
    locates it.

    They also RAISE it now. The launcher is usually still open behind these
    windows, so closing without bringing it forward just revealed whatever
    was underneath - which is what "does not take you back" looked like.

v1.6.16  (2026-08-06)
---------------------
  - FIXED: Finish on the wizard's last screen did nothing.

    Show-Step returns the button handlers for the step it draws. If any
    statement inside a step leaks a value to the pipeline, PowerShell
    returns an ARRAY rather than the hashtable - and $Handlers.Next then
    resolves to $null, so the button silently does nothing at all.

    Go() now takes the last hashtable out of whatever came back and ignores
    anything that leaked, which makes the whole class of bug harmless. If
    it ever does come back empty it now says so instead of failing
    silently.

  - CHANGED: Finish hands you back to the main screen, matching Done in
    Install and repair. If the launcher is already open behind it, it just
    closes.

v1.6.8  (2026-08-06)
--------------------
  - NEW: the mod now checks which Windows it is running on, and says so.

    Install and repair shows it on the first row - "Windows 11 25H2 (build
    26200.8875) - supported" - and refuses to install anything if it is
    not. The wizard checks at step 2 and will not install on an unsupported
    version either.

    The check uses the BUILD NUMBER, never ProductName. On a Windows 11

v1.6.4  (2026-08-06)
--------------------
  - NEW: a text size control in the Settings window. Three stops - 100%,
    115%, 130% - and the choice is remembered.

    It lives in the status bar, on every page, NOT on a settings page.
    Someone who cannot read the app cannot navigate to a page to fix that,
    so the escape hatch has to be where they already are.

    One thing worth knowing about how it behaves. Scaling up SHRINKS the
    usable canvas, because the window cannot grow past the screen. On this
    1707x1019 work area:

        scale 1.00   window 1360x900    canvas 1360x900
        scale 1.15   window 1564x1019   canvas 1360x886
        scale 1.30   window 1707x1019   canvas 1313x784

    At 130% the layout has less room than it was designed for, and parts of
    a page would have been unreachable. The scaled content now sits inside
    a scroll viewer, so at worst you scroll - nothing is ever cut off. The
    trade is that at 130% on a display this size the Save button sits below
    the fold and you scroll to reach it.

  - Settings gained a -RenderTo switch, for checking layout without
    clicking through. That is what caught the clipping above.

v1.6.3  (2026-08-06)
--------------------
  - NEW: icons throughout both windows. Lucide v1.28.0, ISC licence,
    geometry taken from the official SVG rather than hand-drawn.

    Eight on the launcher, eleven on the settings rail, and one glyph means
    one thing across both: gauge is frame rate everywhere, joystick is the
    stick everywhere, wrench is repair everywhere. Deliberately NOT a cog
    for Settings - a cog says "machinery", which is the register this app
    is trying to leave.

    Two conversions are not obvious and both were caught by rendering a
    contact sheet and looking at it, not by assuming:
      * <circle> and <line> carry no "d" attribute and are rebuilt as arcs
        and linetos, because WPF path data has no circle primitive.
      * A leading relative "m" is ABSOLUTE per the SVG spec, but the
        coordinate pairs after it are RELATIVE linetos. Uppercasing the
        command turns them absolute and quietly wrecks cloud-sun, compass,
        gauge, file-cog and clipboard-check.
    Both are documented in assets/lucide-icons.xaml so they cannot come
    back.

  - FIXED: a UAC prompt before every single launch.

    This was never the launcher asking for rights. Bob.exe carried the
    RUNASADMIN compatibility shim, and BOB2_Launch.bat then elevated
    itself "for CPU pinning" - also not the real reason, since
    "start /affinity" can pin a process you create without any privileges.
    The elevation existed only because an elevated child does not inherit
    the affinity mask from a non-elevated parent, so the whole chain had
    to be elevated for pinning to stick.

    The shim is not needed: the game folder grants Authenticated Users

  - FIXED: the launcher reported "currently not rescaled" even when the
    menu rescale had applied perfectly.

    It identified the build by hashing the whole Bob.exe and comparing
    against the output checksum recorded in the patch file. That stopped
    working the moment the Windows 10 import fix below was folded into
    BOB2_MenuScale.ps1, because the import edit is applied AFTER the
    rescale - so the finished executable could never match the recorded
    hash again, whatever scale was chosen.

    The rescale itself was always fine, and BOB2_MenuScale.ps1 was always
    correct: it verifies its checksum BEFORE the import fix. Only the
    launcher's status line was wrong.

    It now asks the file directly - a patch counts as applied when its
    edited 16-bit values are present at their offsets. That stays true no
    matter what else changes elsewhere in the executable, so this class of
    bug cannot come back.

  - INCORPORATED: the community Windows 10 patch turns out to be a nine
    byte change, and a neat one. It renames the imported KERNEL32 function
    DebugBreak to GetVersion.

    The game calls DebugBreak() somewhere. That raises EXCEPTION_BREAKPOINT,
    which Windows XP usually survived and which Windows 10/11 treats as
    fatal when no debugger is attached. Both names are ten characters, take
    no arguments, and return something the caller ignores, so pointing the
    import at GetVersion makes the call harmless.

    This is the same crash the dinput8.dll guard has been catching in a
    vectored handler. The import rename is better: it stops the exception
    being raised at all rather than recovering after the fact. The guard
    stays as a backstop and still handles the SxS case.

    BOB2_MenuScale.ps1 now applies it on every write, so it survives a
    change of menu scale. Verified: Bob.exe no longer imports DebugBreak
    and has two GetVersion entries; Bob.exe.unscaled is untouched.

    "Bob.exe.win10patch", is byte-identical to stock 2.13 - it is a backup

  - NEW: TARGET\BOB2_T16000M.tmc - joystick response curves for
    Thrustmaster TARGET, since the game itself has none.

    The curve is not there to reproduce a Spitfire's control forces; no
    curve can do that on a spring-centred desktop stick. It corrects a
    TRAVEL mismatch. A Spitfire's control column moves roughly 250 mm
    fore and aft; a T.16000M moves about 60 mm. The same hand movement
    therefore commands about four times the control deflection, which is
    why tracking a target feels twitchy. Softening the centre returns
    that resolution where it matters and keeps full authority at the
    stops.

    Three profiles, shaped by what the real aeroplanes actually flew like:
      Spitfire/Hurricane  pitch -30, roll -20. The Spitfire's elevator
        was famously light and pilots over-controlled in pitch, so pitch
        is softened MORE than roll; the fabric ailerons were heavy above
        about 300 mph, so roll is left livelier.
      Bf109E              pitch -20, roll -30. The emphasis reverses: the
        109's ailerons went very heavy at speed while its elevator stayed
        usable.
      Bf110 / bombers     pitch -10, roll -10. Flown on trim rather than
        on the sight, so a soft centre buys nothing and costs authority.

    Rudder carries a 4% deadzone while nothing else does - not for sensor
    drift, which Hall-effect sticks do not have, but because your wrist
    twists slightly whenever you push the stick sideways. Without it you
    feed in rudder every time you roll. Throttle is deliberately left
    linear: half travel should mean half throttle every time.

    The script flags one thing to verify rather than trust - which sign
    of SetSCurve's curvature softens the centre. Load it, look at the
    curve TARGET draws, and confirm the line sags BELOW the diagonal near
    centre; flip the signs if it bulges above.

  - Two consequences of running TARGET, both easy to miss:
      * It presents a VIRTUAL device with a different GUID, so the game
        no longer recognises the stick. Re-run BOB2_Controls.ps1 -Apply
        afterwards to give the virtual device a DeviceDefaults.txt entry.
      * Its deadzone stacks with the game's. BOB2_Sensitivity.ps1 gained
        a 'target' preset that sets the in-game deadzone to zero, so the
        external tool owns it outright.

  - NEW: BOB2_Controls.ps1 - detects what is actually plugged in and sets
    it up. Axis assignment lives in DeviceDefaults.txt, a plain-text file
    keyed by DirectInput device GUID, and the shipped copy dates from
    2005: a Saitek X36, a Saitek X45, a Logitech WingMan and a
    Thrustmaster Top Gun. Any stick made since is unknown to the game,
    which is why its controls screen is so unhelpful.

    The tool reads real axis and button counts from winmm, the product
    name from the driver's registry entry, and derives the DirectInput
    GUID from VID/PID - the GUID is simply PID then VID with a fixed tail
    whose bytes spell "PIDVID", which is how the shipped Saitek entries
    are formed. Dry run by default; -Apply writes, backing both files up
    to _ControlsBackup\<timestamp>\ first.

    It adapts to what is present: a twist-grip stick flown alone keeps
    throttle on its slider, but plug a separate throttle in and re-run
    and throttle moves to the real lever with rudder on the rocker.

    The button preset gives each action EXACTLY ONE device code. The
    stock file binds each action across four notional sticks
    (260/300/340/380); leaving that in place means plugging a throttle in
    later silently makes ITS button 5 do whatever the stick's button 5
    does. Verified afterwards: keys.txt still round-trips byte-identical,
    236 of 236 actions rebuild exactly, and no joystick button maps to
    more than one action.

  - NEW: BOB2_Sensitivity.ps1, and with it the first decode of
    SAVEGAME\inputcfg.dat - 18 records of 278 bytes, one per in-game
    axis in AU_ order:
        +8  int32 device kind  2 joystick, 1 mouse, 0 none
        +12 int32 DEADZONE     0..10000 DirectInput units
        +16 int32 SATURATION   0..10000
        +20 int32 DirectInput axis index, -1 unassigned
        +24 byte  INVERT
        +25 char[] physical axis name
    Confirmed by the four joystick records lining up exactly with pitch,
    roll, yaw and throttle, and by the throttle record already carrying
    the invert flag a slider needs.

    Writes are surgical: applying a preset changed exactly 4 regions of
    2 bytes each, all at offset +12 of a joystick record, file length
    unchanged. Presets and named profiles (save / load / list) live in
    _AxisProfiles\.

  - FINDING: BOB2 HAS NO JOYSTICK RESPONSE CURVES. The entire input path
    is ApplyDeadZone followed by CalibrationScaler and
    CalibrationConstant - a multiply and an offset. No exponent, no curve
    table, no shaping of any kind on a joystick axis. setMouseSensitivity
    exists but is mouse only.

    The Curve class in CURVES.CPP is easy to mistake for it and is not:
    it sits under Release\model\ and serves Engine::SetCurves and
    ModelGenerator::ParseCurves - aerodynamic and engine data.

    So deadzone is the only meaningful in-game lever, and the shipped
    7.5% is a 2005 default sized for potentiometer sticks that wandered.
    A Hall-effect stick does not need it. Real curves have to be applied
    before the game sees the axis - Thrustmaster TARGET or Joystick
    Gremlin with vJoy - both of which present a virtual stick the game
    then reads as linear.

  - IMPORTANT, and the cause of "the menu rescale does nothing": the
    HIGHDPIAWARE compatibility shim. It tells Windows the program manages
    DPI itself and must not be scaled. BOB2 is from 2005 and does no such
    thing, so with that flag set its menus are drawn at true pixel size.
    On a 2560-wide display at 150% scaling that is about a third smaller
    than intended - and it exactly cancels the menu rescale. The dialogs
    really are larger; Windows has simply stopped magnifying them.

    It is easy to acquire by accident, since Properties > Compatibility >
    "Change high DPI settings" > "Override high DPI scaling behaviour"
    sets precisely this flag. The Win11 tweaks step has never added it,
    but it now actively REMOVES it and says so, rather than leaving a
    stray flag to defeat the rescale silently.

    This is also why a rescaled prototype looked right while the same
    bytes installed as Bob.exe did not: the prototype had no compat
    entry, so Windows scaled it 1.5x on top of the 1.40x rescale. Same
    executable content, different environment. Comparing checksums could
    never have found it.

    read-then-write reproduces bdg.txt, keys.txt and Weather.cfg
    byte-for-byte identically (21179 / 4363 / 53 bytes), all 350 bdg
    assignments and all 236 key actions rebuild to exactly the line they
    were parsed from, and the tool opens with zero pending changes and
    Save disabled. Lines are rebuilt by concatenating captured groups
    rather than by regex substitution, so a '$' or '\' in a value cannot
    corrupt the line. Nothing is written until Save; every file that is
    about to change is copied to _ConfigBackups\<timestamp>\ first.

    It also found a conflict shipped in the file itself: End is bound to
    both EXITKEY and LOOKS.

  - NEW: BOB2.bat - a launcher window, and from now on the only file you
    need to run. Play, Settings, Measure Frame Rate, Graphics Wrapper and
    Setup are all reachable from it, and Full Install puts a "Battle of
    Britain II" shortcut on the desktop pointing at it.

    This is not decoration. The package had grown to five loose .bat files
    whose correct running order was never stated anywhere, and one of
    those orderings silently destroys work: Bob.exe REWRITES bdg.txt and
    settings.cfg when it exits, so anything the configurator changes while
    the game is running is discarded on quit. bdg.txt even documents a
    case of this against itself -

        ENABLE_AUTO_TEXTURE_RES=ON  # Change to 'OFF' will affect one
                                    # session only, IOW BoB will write
                                    # 'ON' back over it.

    The launcher fixes that structurally rather than by documenting it.
    It polls for Bob.exe every two seconds and greys out whatever is
    unsafe at that moment:
      * game running     -> Settings, Play, Wrapper and Setup disabled
      * game not running -> Measure Frame Rate disabled, because a
                            PresentMon capture taken at a menu measures
                            nothing (the menu barely renders)
    Each disabled button says why, so it reads as an explanation rather
    than as something being broken.

    It also surfaces state that previously required reading files by
    hand: game version, installed fix version (flagged amber when it is
    older than the package), and which d3d9.dll is actually in place,
    with its version, in red if it is not dgVoodoo2.

    The Graphics Wrapper button opens a chooser rather than a console
    window, and explains the trade-off - native D3D9 has lower CPU
    overhead, which matters on a CPU-bound engine, but crashes on
    entering 3D on most modern systems.

    Not self-elevating. The window needs no privileges; it elevates only
    the actions that genuinely do (Play, for CPU pinning; Measure FPS, to
    trace an elevated process; Setup, to write into the install folder).

v1.2.1  (2026-08-04)
--------------------
  - IMPORTANT: the crash guard no longer tries to "repair" access
    violations inside RCombo.ocx (the control behind the "More GFX"
    options tab). It logs them and lets the game's own exception handler
    deal with it.

    Why: earlier builds set EAX=0 and advanced EIP by 2 to step over what
    was believed to be a single null-pointer dereference. A real crash
    showed that does not work - the log recorded a fault at offset 0x2944,
    the skip, then an immediate second fault at 0x2946, because the next
    instruction uses the same bad pointer. Execution then continued into
    code that could not cope and jumped to address 0x00000003. The
    "repair" turned a contained fault into corrupted control flow.

    You cannot fix a null-pointer dereference by stepping over one
    instruction when the surrounding code assumes the pointer is valid.

    Breakpoint and SxS handling are unchanged - those ARE safe to skip.

v1.2.0  (2026-08-03)
--------------------
  - FIXED: the bundled dgVoodoo.conf shipped VRAM = 4096. Era-appropriate
    D3D titles can fail to start with implausibly high emulated video
    memory, and it matched neither the known-good config nor dgVoodoo2's
    own default. Now 256. (Found by running Full Install against a
    throwaway copy of a game folder.)
  - FIXED: a PowerShell array-flattening bug made the Win11 tweaks step
    print "[OK] O already enabled" instead of the setting name. A
    single-element array of arrays is flattened, so indexing returned
    single characters.
  - Full Install now applies BDG v2.13 ONLY. BDG's own release notes say
    v2.13 brings any previous version up to date and includes MultiSkin,
    so the old 2.12 -> MultiSkin -> 2.13 chain required about 500 MB of
    extra downloads and achieved nothing. Those steps are still available
    under "Individual Steps". Quick Start now lists two downloads
    instead of four.
  - Full Install warns before patching that campaigns from earlier
    versions will not load in 2.13 and that SAVEGAME must be cleared
    except DIR.DIR / inputcfg.dat / settings.cfg, and that Windows text
    scaling should be 100%. Both are in BDG's notes and easy to miss.
  - README rewritten where it was wrong: the video crash is a missing
    Indeo 5 codec (not an mpg2splt.ax null-pointer bug), and there is now
    a proper explanation of why dgVoodoo2 is REQUIRED rather than
    optional - the game asks for an invalid 0x0 fullscreen buffer, which
    native D3D9 and DXVK both reject, crashing the game.
  - README documents the DirectX 9.0c requirement (d3dx9_35.dll) and the
    four helper scripts, which previously shipped undocumented.
  - Status report no longer says "dgVoodoo2 DLLs 4/4". Only D3D9.dll is
    load-bearing; it now reports that file and its version, and treats a
    missing D3D9.dll as an error rather than a partial install.
  - FIXED: the tool shipped OBJECT_DENSITY=4 and PARTICLE_DENSITY=4 while
    reporting "Applied performance settings". Those are the MAXIMUM-COST
    quality values and the single biggest frame-rate cost in this engine.
    BOB2 is CPU-bound - measured on a 13900HX / RTX 4080 the CPU spends
    about 3x longer per frame than the GPU - and ground-object count is the
    dominant CPU load. Defaults are now density 2 with the scenery
    generators off. Measured effect of that change plus correct CPU
    pinning: median frame rate 28 -> 76 FPS.
  - "Win11 tweaks" no longer forces ENABLE_AUTO_GEN=ON and
    ADD_SHEEP_COWS_AND_HAYSTACKS=ON. Those are scenery generators, not
    compatibility fixes, and bundling them into that step silently cost
    frame rate. They are now controlled only by the Settings Tweaker.
  - Presets rebalanced and now honest about cost:
      Performance = density 1, no generated scenery, 1024 terrain textures
      Balanced    = density 2, no generated scenery  (recommended)
      Quality     = density 4, generated scenery on, with an explicit
                    warning that it roughly halves frame rate
  - bdg.txt edits are now anchored to line starts, so a key that merely
    CONTAINS another key's name is no longer corrupted, and settings that
    are missing from the file get appended instead of silently skipped.
